# tmux MCP 消息控制台设计

## 目标

把“消息模式”从操作时间线改为命令对话界面：

- AI 与网页人工命令都在同一消息流中显示。
- 网页先在本地输入完整命令，再一次性发送到所选 pane。
- 同一张命令卡从运行中更新为完整输出、退出码和耗时。
- 交互模式保持现有 tmux 快照和逐键转发行为。
- 整体改成白色、简洁的 ChatGPT 风格。

## 命令与逐键输入的边界

消息模式只承诺展示有明确开始/结束边界的命令输出：

- AI `execute-command`：保持现有记录方式。
- 网页消息输入框：通过现有 `CommandTracker` 执行并记录，来源为“你”。
- AI 或人工 `send-keys`、方向键、Tab 等：仍显示为输入记录；其输出无法可靠归属到某次输入，不猜测、不伪造。

这避免从 `capture-pane` 屏幕差异推断输出。屏幕差异会受提示符刷新、
异步程序及 AI/人工并发输入影响，无法保证完整或不重复。

## 服务端

网页进程复用已有 `CommandTracker`、`SecurityPolicy`、SSH、socket 和
终态输出清理，不创建另一套 shell 包装协议。

新增：

- `POST /api/panes/{paneId}/commands`
- 请求体：`{"command":"..."}`。
- 命令必须非空、是单条 shell 命令，并通过现有 tool、socket、pane、
  session 和 command 安全检查。
- 网页人工命令绕过 Gate，与现有网页逐键输入一致。
- 接受后立即返回命令 ID；后台监听现有 tracker 事件，用同一记录 ID
  更新运行中和最终 `CommandSnapshot`。

网页 tracker 只调度网页提交的命令；各 MCP 进程仍保持自己的 tracker。
不同来源同时操作同一 pane 时继续显示干扰提示，不增加跨进程调度器。

## 页面

消息模式底部固定一个本地命令输入框：

- 选择 pane 后启用；未选择时禁用。
- Enter 发送，发送成功后清空并恢复焦点。
- 请求失败时保留原命令并显示现有错误条。
- 命令运行期间可以继续提交；同一网页 tracker 按 pane 复用现有队列。
- 现有逐键输入只留在交互模式。

首版保持单条 shell 命令，不支持换行命令；现有 tracker 明确拒绝换行，
不为输入框绕过这项安全约束。

## 视觉

- 白色主背景，浅灰侧栏与分隔线。
- 消息区居中并限制宽度，减少厚重卡片边框。
- 人工命令使用浅灰气泡；命令输出使用白底正文块。
- 底部输入框使用圆角、轻阴影和黑色发送按钮。
- Gate、pane 导航、审批框、操作日志及状态语义保持不变。
- 保留键盘焦点样式、标签及安全的 `textContent` 渲染。

## 验证

- API 拒绝空命令、未知 pane 和违反安全策略的命令。
- 人工命令只产生一条记录，并在终态包含干净输出、退出码及耗时。
- 同一 pane 的网页命令继续按现有 tracker 顺序执行。
- 页面 Enter 提交、失败保留、成功清空，交互模式行为不变。
- 白色主题、输入框及无 `innerHTML` 由静态 UI 测试覆盖。
- 在临时 tmux pane 中完成一次浏览器端命令与输出验收。
